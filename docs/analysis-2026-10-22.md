## 3. P0

### 3.1 单实例锁缺失，第二个实例会「误杀」正在跑的任务

- 证据：`main.go:39-70` 的 `options.App` 没有 `SingleInstanceLock`（全仓 grep 0 命中）；启动流程 `app.go:558` 调 `s.MarkInterrupted(ctx, time.Now())`，把「上次退出时未结束」的任务全部落库为 `interrupted`。
- 后果：双击两次快捷方式 → 两个进程共用一个 `%AppData%\FFmpegFree\app.db`；第二个实例启动即把第一个实例**正在运行**的任务标成中断，任务中心的进度 / 重试入口全部错乱。
- 修复（一行）：
  ```go
  SingleInstanceLock: &options.SingleInstanceLock{UniqueId: "ffc-desktop"},
  ```
- 建议顺便验证：第二个实例被拒绝时给用户提示，而不是静默退出。

### 3.2 没有 `OnBeforeClose`，`OnShutdown` 同步阻塞最多 16 秒

- 证据：`main.go:56` 只注册了 `OnShutdown: mainApp.shutdown`；全仓没有 `OnBeforeClose`（grep 0）。`app.go:574-604` 的 `shutdown` 依次停调度器、`c.Wait()`、`convert.Close(3s)`、`m.Shutdown(wait)`；有带存档直播时 `wait = 16 * time.Second`（`app.go:598-602`）。
- 后果：窗口先消失、进程再卡十几秒；用户以为卡死 → 强杀，恰好打断正在写的存档尾，与这段代码想保护的东西相反。
- 旁证：`app_window.go:39` 的 `hideWindow()` 生产代码零调用，只有 `app_window_test.go:37,54` 调 → 「关到后台 / 托盘」的设计没接上。
- 修复：`OnBeforeClose` 拦截 → 显示「正在结束任务…」→ 等 `m.Shutdown` 返回再放行；或把 shutdown 改成异步 + 进度事件。

### 3.3 群聊写任务被静默降级为「只读」

- 证据链：
  1. `internal/service/cat/group_route.go:321`：`detail, _ = s.cfg.Store.InsertCatGroupRoute(...)` —— 错误被丢弃，失败时 `RouteSeq` 保持 0；
  2. `internal/service/cat/group_coordinator.go:135`：`detail, _ := s.cfg.Store.GetCatGroupRoute(routeCtx, route.RouteSeq)` —— 再用 0 去取，拿到空 `OutputText`；
  3. `group_coordinator.go:52-67`：`groupDecisionCapability` 从空文本解析不到 capability，没有任务时落到 `return "read_only"`。
- 后果：用户让它改代码，它只分析不改，且**不告诉用户为什么**；排查时日志里也没有线索。
- 修复：两处 `_ =` 都改成显式处理；插入失败就让本次派活失败并回一条可见灰字（或至少 `Logf` + 标记 `capability=unknown` 让前端提示）。

### 3.4 DAG 节点 wake 失败后永久「排队中」

- 证据：
  - `group_workflow.go:318` 把节点置为 `queued` 并落库；
  - `group_turn.go:116-119`（claim 失败 / 出错）与 `191-195`（turn 启动 claim 失败）都是**静默 return**，不回滚 `queued`、不改 `blocked`、不重试；
  - 会话内没有对 `queued` 的重扫：`readyGroupTasks` 只取 `pending`，`recoverGroupWorkflows`（`group_workflow.go:706`）只在启动时每群跑一次。
- 后果：该节点永久排队，依赖它的后续节点永久等待；用户看到不动的进度条，重启应用才能恢复。
- 修复：wake 失败改 `blocked` + 可见原因（更符合现有语义），或加带超时的 reconcile 看门狗。

### 5.2 `catagent` 测试绕过注入的 `LookPath`

`internal/catagent` 的 `TestDetect_MissingWithoutGrok` / `TestClaudeDetect_Missing` 在 Windows 上返回 `State:ready Version:1.0.52 / 2.1.300` —— `cfg.LookPath` 注入的 `ErrNotFound` 没生效，检测走到了 Windows 的 `winlookup` / 真实 `PATH`，把**本机**安装的 CLI 当成结果。影响：本机装了 CLI 的开发者永远看不到这两个用例红（漏 bug），CI 上没装则过。建议给 Windows 检测也走可注入的查找接口。

### 5.3 无 `.gitattributes`

`core.autocrlf=true` + 无 `.gitattributes` → 工作区 CRLF。gofmt 整文件报 diff（上一版已记），本次又确认它让 `check:api` 的 3 条源码正则失配（4.3）。加 `.gitattributes`（`*.go text eol=lf` 等）能一次性消掉两类噪声。
