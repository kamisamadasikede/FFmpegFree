# ffc（Wails v2 桌面端）项目分析

日期：2026-10-21　分支：`v2`　工具链：Wails v2.16.0 / Go 1.25.0 / Vue 3 + Vite 5

> 本版针对「Wails 桌面应用」重新组织结论。上一版按通用 Web/服务端项目评判，有几处判断需要修正，见第 0 节。

## 0. 对上一版的修正

| 上一版说法 | 实际情况 |
|---|---|
| 「576 个 Go 文件未 gofmt」 | **错**。这 576 个文件是 CRLF 换行，gofmt 因此整文件报 diff；把文件转回 LF 后 gofmt 无改动。真实问题是仓库没有 `.gitattributes`，Windows checkout 会把 LF 变 CRLF，于是每次 `git status` 刷 `LF will be replaced by CRLF` 警告、gofmt 也会误报。 |
| 「没有 CI」列为 P0 | **降级**。单人维护的桌面应用没有 CI 是常态；真正 P0 的是打包与运行时问题（单实例、关窗、版本资源、陈旧产物）。测试红的问题换个说法更准确：**测试是按 Linux 写的，而这是 Windows 桌面应用**，等于对主平台没有防护。 |
| 「`callService` 用了 161 处」 | 数字不准。精确统计：`callService` 调用点 **63 处**、`hasServiceBinding` 5 处、裸 `window.go` 引用 **49 处**、直接 import 生成绑定的文件 **39 个**。结论方向不变（类型安全被绕过），但量级要按这个。 |

## 1. 基线

- 11 个 Wails Service（`App` + 10 个领域 Service）共 270 个导出方法，全部反射暴露给前端。
- 后端不监听端口，唯一 HTTP 是 AssetServer 上的 `/local/<token>` 本地文件预览（token 128 位随机、每次请求 `EvalSymlinks` + `os.SameFile` 复核，Windows 上 Range 上限 4 MiB / 整文件 32 MiB）。这块设计是好的。
- 前端 dist 与 `internal/genoffice/runtime` 一起被 `go:embed`，单文件产物 124.1 MB。
- 22 个 SQLite 迁移、39 个错误码、契约 `contract.md` 5 784 行（v0.57）。

## 2. 构建链路实测

| 步骤 | 结果 |
|---|---|
| `npm run build`（vue-tsc + vite） | ✅ 32.2 s，dist 13.4 MB |
| `wails build -platform windows/amd64` | ✅ 1 m 39 s → `build/bin/ffc.exe` **124.1 MB** |
| 绑定生成 | ✅ 完整。`CatService`：Go 143 个导出方法 vs 生成 141 个，差的 2 个是私有 `rootCtx`/`svc`，无缺失 |

产物元数据（读 exe 版本资源）：

```
FileVersion    = 1.0.0
ProductVersion = 1.0.0
ProductName    = ffc
CompanyName    = ffc
LegalCopyright = Copyright.........        ← 模板占位没填
签名            = NotSigned
```

`wails.json` 的 `info` 只写了 `productName`，而 `build/windows/info.json` 模板还引用了 `ProductVersion` / `CompanyName` / `Copyright` / `Comments`，于是落到 exe 里就是占位文本。同时 `scripts/build.ps1` 里是裸 `wails build`，没有 `-ldflags "-X FFmpegFree/internal/about.Version=..."`，所以「关于」页永远显示「开发版」。

## 3. Wails 特有的真问题

### 3.1 嵌入的 dist 是两天前的（已复现，已修）

`//go:embed all:frontend/dist` 是**编译期**嵌入，而 `frontend/dist` 被 gitignore。实测发现 dist 最新文件 10-19 18:59，而 `src` 最新改动 10-21 12:54 —— 任何人在这期间跑 `go build` / `go test`，拿到的都是旧界面。README 提过这个坑，但没有任何机制拦住它。

已在本机执行 `npm run build` 刷新，现在 dist 与源码同步。

建议：`scripts/build.ps1` 里显式先构建前端；并在 `wails build -skipbindings` 场景下加一条「src 比 dist 新就报错」的检查。

### 3.2 前端大面积绕过生成的绑定

Wails 的核心价值之一是 `wails generate module` 给出带类型的绑定。这里：

- `frontend/src/api/call.ts` 的 `callService(service, method, ...)` 用**字符串方法名**通过 `window.go.app.<service>.<method>` 反射调用，共 **63 处**；
- 另有 **49 处**直接摸 `window.go`；
- 只有 **39 个文件** import 生成的 `wailsjs/go/app/*`。

`call.ts` 里写明了理由：「后端还没有这些绑定时不能 import 生成文件（vue-tsc / vite build 会找不到模块）」。但实测绑定已经 100% 齐了 —— 这个兼容层现在只剩成本：Go 端改方法名或参数，`vue-tsc` 抓不到，要到运行时才抛 `UNSUPPORTED`。

建议：把 63 处 `callService` 里走「真实后端」的部分改回 `import * as XxxBinding`，只让纯浏览器模拟层保留字符串路由。

### 3.3 没有 SingleInstanceLock

`options.App` 里没有 `SingleInstanceLock`（全仓 grep 命中 0）。双击两次快捷方式 → 两个进程共用 `%AppData%\FFmpegFree\app.db`，而启动流程会把「上次退出时未结束的任务」标成 `interrupted` —— **第二个实例会把第一个实例正在跑的任务误判为中断**。桌面端这是用户随手就能触发的。

Wails v2 有现成选项，代价一行：

```go
SingleInstanceLock: &options.SingleInstanceLock{UniqueId: "ffc-desktop"},
```

### 3.4 没有 OnBeforeClose，而 OnShutdown 会阻塞 16 秒

- 全仓没有 `OnBeforeClose`（命中 0），关窗即退出。
- `shutdown` 里 `m.Shutdown(wait)` 是同步等待，有带存档的直播时 `wait = 16 * time.Second`（写完存档尾）。
- 结果：窗口先消失、进程再卡十几秒。用户看到的是「点了关闭没反应」，很可能直接强杀 —— 恰好把正在写的存档打断，和这段代码想保护的东西相反。
- 旁证：`hideWindow()` 定义了，但**生产代码里一次都没被调用**（只有 `app_window_test.go` 调），说明「关到后台 / 托盘」的设计没接上。

建议：用 `OnBeforeClose` 拦截 → 先弹「正在结束任务…」→ 等 `m.Shutdown` 返回再放行。

## 4. 桌面端约定与发布缺口

| 项 | 现状 |
|---|---|
| 安装包 | 无。`build/windows/` 下只有 `icon.ico` / `info.json` / `wails.exe.manifest`，没有 `installer/`，`wails build -nsis` 用不了 |
| 代码签名 | 未签名 → SmartScreen 会拦首次运行 |
| WebView2 | 没有依赖声明与引导策略；面向 Win10 老版本 / LTSC 需要 bootstrapper 或 NSIS 内嵌 |
| 升级通道 | 无应用级自动更新（`releases/latest` / `CheckForUpdate` 命中 0，只有各家 CLI 的版本检测） |
| 窗口状态 | 不记忆位置与大小（Wails 需自己存，命中 0） |
| 托盘 / 菜单 | 无 `menu.NewMenu`、无托盘（命中 0） |
| 陈旧产物 | `build/bin/FFmpegFree-dev.exe~`（52 MB，10-13）、`FFmpegFree.exe`（27 MB，10-08）是改名前的残留，`-clean` 未启用 |
| 目录残留 | `build/bin/output`、`build/bin/uploads` 存在，与 README「开发时不应在 build/bin 里创建」矛盾 |

## 5. 与 Wails 无关但仍然要处理

1. **Windows 文件名净化有洞**：`a:b'c&d.mp4` 转换后 `rename` 失败（`The parameter is incorrect`）。`internal/fsutil` 有能力做净化，但输出改名路径没接上。这是 Windows 专属真 bug。
2. **测试按 Linux 写**：`go test ./...` 19 包过、12 包挂、42 个用例失败。多数是路径分隔符、`/in.mov` 当绝对路径、`-rw-rw-rw-` 权限位、日志引号这类 Linux 假设 —— 对一个 Windows 桌面应用，这批测试基本失去意义。
3. **README / 契约漂移**：README 说视频剪辑已完成且 `EDIT_BACKEND_READY=true`，实际 v0.23.5 已整体移除、`internal/service/edit` 不存在；说 `DOC_BACKEND_READY=false`，实际 `flags.ts` 是 `true`；说 Go 1.24，实际 1.25；开关表列 3 个，实际 15+；**整份 README 没有 Cat 子系统**，而 Cat 已是最大子系统。契约停在迁移 `0019`，代码已到 `0022`。
4. **ffmpeg 许可证**：仓库入库 154 MB ffmpeg 二进制（`avcodec-62.dll` 单文件 102 MB），`build.ps1` 还把它拷进产物；实测是 `--enable-gpl --enable-libx264` 的 GPL 构建，而项目是木兰宽松许可证 —— 与 README「不随安装包分发」的说法也不一致。
5. **仓库卫生**：`desktop/` 401 MB 只有 `node_modules`（未入库、无源码，可删）；根 `node_modules` + 根 `package.json` 只为一个没人引用的 `pdfjs-dist`；`packages/pptx-engine` 仅 2 个文件却被 `office/vendor/slides/**` 用跨目录相对路径引用。
6. **前端自检两红**：`check:api` 7 处（其中 4 处是 `JSON.stringify` 键序敏感导致的假失败）、`check:copy` 8 处（`catState.ts` 里出现 Codex / Claude / CLI 等被禁词）。

## 6. 建议顺序

**P0（桌面端会直接踩到的）**

1. 加 `SingleInstanceLock`
2. 加 `OnBeforeClose` + 关窗进度提示，避免 16 秒「假死」
3. 补 `wails.json` 的 `info`（版本、公司、版权），`build.ps1` 注入 `-ldflags` 版本号
4. 清掉 `build/bin` 陈旧产物，构建脚本加 `-clean`

**P1**

5. 把 `callService` 的 63 处真实调用回收成类型绑定
6. 给 dist 陈旧加防护（构建脚本强制先 build 前端）
7. 修 Windows 文件名净化与重转 `output_moved` 误判

**P2**

8. 签名 + NSIS 安装包 + WebView2 策略
9. 测试改成 Windows-first（或按平台加 build tag 分开）
10. 同步 README / 契约

**P3**

11. 仓库瘦身（ffmpeg 移出 git、删 `desktop/`、收编 `packages/pptx-engine`）
12. 明确 ffmpeg GPL 的合规边界
