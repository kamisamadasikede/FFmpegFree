# 群聊协调与任务接管改造方案

更新日期：2026-10-21。范围：现有群聊路由、对话上下文、任务生命周期和前端交互。

状态：已按审核后的分期落地第一期“统一入口、固定输入、可靠派发与权限边界”。第 4–10 节保留完整目标设计，其中话题关联、复合操作、独立主答通道和结构化交接尚未实现；实际代码、验收结果及限制以第 11–13 节为准。

## 1. 目标与建议

所有有效用户消息，包括有 @、无 @、追问、附件和停止后的新消息，都进入统一协调分析。协调器判断用户在对谁说话、在讨论什么、需要谁回答、是否需要执行任务，以及如何关联已有工作。

推荐：后台有状态协调器 + 按需成员发言 + 复用现有执行器和任务依赖图。协调器负责组织对话，成员仍以自己的身份回复。先改现有 Go 系统，无需为这一需求迁移到 Python 或引入新的多 Agent 框架。

基本约束：

- 每条已接收消息有可追踪的回复责任；接收回执不等于已回答。
- @ 是重要的收件意图，必须参与分析；不能直接绕过分析，也不能被协调器随意忽略。
- 默认一位主答成员；需要多人时允许补充和交接，明确要求全员发言时安排全员。
- 普通对话与工具执行分开；进度询问、招呼和讨论不自动创建开发工作流。
- 用户的停止、只分析不改、仅让某成员处理等明确限制由程序校验。
- 成员不可用时，系统明确告知，不能伪造成员已经接受或完成任务。

## 3. 官方方案调研及适用性

原方案调研引用以下官方文档，模式用于解释设计取舍；本次实施未重新开展框架调研：

1. Microsoft AutoGen，Selector Group Chat：https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/selector-group-chat.html
   - 根据共享历史和成员描述选择下一位发言者，成员回复广播到团队，再检查终止条件。
   - 支持自定义候选人函数与选择规则。借鉴动态发言选择和停止条件，不照搬默认禁止连续同人发言；本项目的连续追问应允许原成员接着答。
2. LangChain，Multi-agent：https://docs.langchain.com/oss/python/langchain/multi-agent/index
   - 区分 Router、Subagents、Handoffs 和自定义工作流，模式可以组合。
3. LangChain，Router：https://docs.langchain.com/oss/python/langchain/multi-agent/router
   - 区分一次性分类路由与持续对话协调；有状态多轮处理需要跨调用保存上下文。
   - 本项目不能只扩大单次 RouteSchema，还需持久化对话和回复状态。
4. LangChain，Handoffs：https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs
   - 通过显式状态变化切换流程或活动 Agent，交接时控制传递上下文。
   - 借鉴结构化交接；成员输出的 @ 文本仅作为建议，不能直接拥有调度权。

上述是模式依据。下面的 Go 数据模型、交互和迁移步骤是结合本仓库提出的设计，未声称是这些框架的默认保证。

## 4. 统一处理链路（完整目标）

```mermaid
flowchart TD
    U[用户消息：文字、@、引用、附件] --> I[落库、去重、立即返回接收回执]
    I --> C[协调器：意图、话题、主答、任务关联]
    C --> V[程序校验与版本检查]
    V --> D{决定如何处理}
    D --> R[短回复、澄清、进度答复]
    D --> T[新任务、补充、改派、协作计划]
    T --> E[复用现有队列、CLI、重试和工作流]
    E --> O[结构化结果与执行事件]
    R --> O
    O --> N{是否需要其他成员补充}
    N -->|需要| C
    N -->|已答复或等用户| F[收束并更新回复责任]
```

实现为每群串行的决策提交队列，保证相关消息的顺序和状态一致；成员的耗时执行不占用这个队列。模型调用不持有全局锁。用户继续输入时先持久化，后续决定基于快照版本提交，过期决策重新评估，不能拿旧结论覆盖停止或新要求。

独立、互不修改相同资源的任务可以并行。不要为了问一句进度，等待当前写文件任务结束；简单状态问题优先依据可靠执行快照回答。需要模型回答时采用受限的无工具短回复通道，不占用原成员正在执行的 native session；此通道是新增能力，需验证适配器支持，不能假定现有共享会话能安全并行。

## 5. @ 的准确语义

| 输入 | 协调结果与用户体验 |
| --- | --- |
| `@前端 介绍一下你自己` | 前端是明确回答对象，前端回复 |
| `@前端 查一下数据库连接失败` | 分析后由后端主接，简短说明按职责转交；前端只在涉及界面时参加 |
| `@前端 只要你帮我分析，先别转交` | 尊重限制；前端解释或澄清，不自动叫醒其他人或执行修改 |
| `@前端 @后端 登录失败帮我修复` | 一位主负责人；按证据确定两人的工作，必要时协作，避免重复执行 |
| `继续，错误提示也改一下` | 关联上一项需求，生成补充指令；不能直接建立无关新工作流 |
| `现在进度怎样` | 回答当前相关任务状态，不重新执行原任务 |
| `大家介绍一下自己` | 全员顺序或有序发言，不建立开发 DAG |
| `先停这个，换个问题` | 取消明确目标工作；新问题单独分析，旧结果不能恢复被停止任务 |
| 仅发图片 | 分析图片和上下文；可解读或提问，不能自行假设需要改代码 |

如果用户明确要求特定成员执行且能力不足，由该成员回答限制或询问是否需要协作。普通 @ 不应默认等价于“禁止协调”；明确禁止转交则是约束。

## 6. 决策契约与上下文

以下是后续完整契约的概念示例，并非当前 API。审核要求不能用一个互斥 action 表达“停止旧任务并启动新任务”，实际演进以 Operations 数组为基础，再为每种操作定义独立校验；当前仅实现 assign。示例字段如下：

```json
{
  "schemaVersion": 1,
  "intent": "new_task",
  "action": "start_task",
  "topicId": null,
  "relatedRequestId": null,
  "targetTaskIds": [],
  "attentionMemberIds": ["frontend-id"],
  "replyOwnerId": "backend-id",
  "participantIds": ["backend-id"],
  "executionMode": "single",
  "constraints": {"allowTools": true, "allowEdits": true},
  "reason": "涉及数据库连接，由后端处理",
  "replyInstruction": "先说明接管原因，再报告排查结果",
  "tasks": []
}
```

intent 建议覆盖：chat、question、new_task、followup、add_requirement、status、cancel、reassign、broadcast。action 建议覆盖：reply、clarify、start_task、update_task、report_status、cancel_task、reassign_task、start_workflow。只有需要实际开发协作的决定才沿用现有 develop / integrate / verify DAG；不要给所有意图强行套同一 schema。

`topicId=null` 表示需要新建，由程序生成 ID。成员 ID、话题、目标任务等只允许引用当前快照中的真实对象；不要让模型凭空生成已有对象标识。`constraints` 是模型理解结果，最终权限取用户明确限制与现有授权策略的更严格约束，模型不能提升权限。

每次决策至少读取：

- 当前完整消息、结构化 mentions、引用与附件；原消息全文可检索，长文本按预算处理，明确标记截断。
- 最近对话，保留 seq、speakerId、topicId、requestId、replyTo 和时间。
- 当前相关话题摘要、目标、未决问题；摘要保存来源消息序号。
- 活跃任务负责人、状态、执行轮次、最近进度、停止信息和用户补充。
- 成员职责、可用性、能力和工具/编辑限制；忙碌状态是调度因素，不能为追求空闲强行交给不合适成员。
- 近邻上下文和明确引用优先，再查询历史话题；两个候选任务都合理时提出一次具体澄清，不随意改动任一任务。

程序校验：主答成员必须有效；action 与允许副作用一致；关联对象属于本群；停止版本未过期；任务依赖合法；同一用户消息不能重复分派。无效结构输出可修正重试，仍无效时进入可见降级，不静默失败。

## 7. 持久化对象与可恢复状态

避免把全部语义压到 ChainID：

| 对象 | 建议含义 |
| --- | --- |
| Message | Seq 继续标识消息；增加 clientMessageId、replyToSeq、topicId、requestId |
| Request | 一条用户输入的回复责任、处理意图、主答成员及 answeredByMessageSeq |
| Topic | 持续讨论的目标、摘要、关联任务、最近相关消息 |
| Assignment | 某成员本次被要求回答或执行什么、输入快照、状态和版本 |
| Task / Workflow | 实际工作目标和依赖；沿用现有持久化工作流能力 |
| Turn | 单次 Agent 尝试；重试新建 Turn，不重复创建原始需求 |

ChainID 保留为兼容的执行关联键。新消息总有自己的 Request，追问/补充可通过关系表关联相同 Topic 和 Task。一次回复可关联多个 Request，但每个 Request 的履行关系必须明确。

消息接收、Request 和协调待办写在同一事务中，再返回成功；使用持久化待办/事务 outbox 与 clientMessageId 唯一约束，防止返回成功后崩溃丢任务、超时重发重复执行。重启可以恢复尚未开始的协调判断；涉及副作用的运行中任务按现有中断处理核实结果，不能盲目重放。

Request 状态：received → analyzing → assigned → answered；需要用户信息时 waiting_user；不可恢复时 failed_notified；用户取消时 cancelled。接单确认只能把任务推进到 assigned，不能标记 answered。

执行状态仍使用既有 queued/running/retry_wait/succeeded/failed/stopped 等语义。等待、失败与停止必须保留可解释原因。所有 Agent 均不可用时，系统直接显示实际原因并保留回复责任，提供重试入口；不能承诺物理上不存在的 Agent 回复。

## 8. 连续发消息、补充与停止

- 发送接口完成落库后立即返回。前端按消息 ID 展示接收/分析/答复状态，输入框不等待模型调用。
- 每群决策有序，但执行异步；“补充要求”可更新尚未开始的 Assignment。
- 已运行的任务若不能安全动态注入，就保存补充，在下一安全边界处理，或取消后核实已有改动再续跑；明确告知“补充已收到，当前步骤结束后处理”。不能声称运行中的 CLI 已经看见新消息。
- 停止命令和停止按钮均具有控制优先级；歧义时确认目标，不停止全部无关任务。明确停止先建立取消屏障，再处理对话答复。
- 新消息只影响明确关联对象；“现在进度怎样”不得默认恢复旧任务。
- 保留已实现的队列代际隔离、旧结果丢弃、native 会话清理、自动重试和工作流状态版本校验。
- 沿用当前路由 2 分钟预算、native 空闲 10 分钟及执行自动重试策略。协调器重试与执行重试分别计数，并设总预算，避免多层叠加无限重试；这些预算后续通过观测调优，不在本次方案中暗自缩短。

## 9. 成员交接与自动收束

新增结构化成员结果，至少包括 status、summary、evidence、requestedHandoffs、relatedRequestIds、needsUserInput。兼容现有报告与任务状态块。

“交给谁”仍可作为展示文本，但不直接触发 wakeMember。协调器接收 handoff 请求和结果，校验是否仍有未解决目标、下一成员是否提供新贡献、有没有重复处理，再决定接棒、汇总或等待用户。

防循环不仅看最大 hop：记录 request + task + assignee + inputRevision；相同输入版本不能重复分派，除非明确重试。设置每请求的交接次数、模型调用/时长预算；到限时主答说明已完成什么、卡在哪里和下一步，保留可续接状态，不要求用户重新描述全过程。

工作流进度、重试等普通事件由确定性逻辑更新，不为每条工具日志调用协调模型；只在任务完成、阻塞、交接建议或新用户消息等决策点调用。

## 10. 聊天和工作面板交互

- 未选定成员时显示系统接收状态；选定后，明确显示该成员已接单或已排队。
- 主答成员直接用自然语言回答；内部 JSON、选人推理和重复系统日志放在可展开详情中。只展示简短分工理由，不展示模型思维链。
- 每条用户消息可见“分析中 / 某成员负责 / 等你补充 / 已答复”，接收回执与实际回答区分。
- 支持引用回复和“补充到这项任务”；话题关联可以自动选择，用户可以纠正。
- 顶部仅显示活跃执行和自动重试等待；失败、停止与完成进入历史并可移除展示。请求澄清放在聊天中，不伪装成正在运行的开发任务。
- 普通进度查询优先复用真实执行快照，成员繁忙时仍能答状态；不要伪造工具进展。

## 11. 审核后第一期：已经实现

### 11.1 接收与协调

所有有效新消息（有 @、无 @、图片、关闭 AutoRoute 的群）先保存用户消息和请求，再立即返回接收结果。系统先显示“收到，正在分析这条消息并安排成员回复”，成员开工前再发送接单确认。协调模型在后台执行，不占用发送接口等待时间。

@ 进入模型输入，普通专业请求允许按职责转交；明确“不要转交”“只让你”“介绍自己”等保守短语会固定被 @ 成员，并移除不符合限制的开发计划。协调失败优先选择已就绪的关注成员，再考虑其他已就绪成员；明确禁止转交时兜底范围也限于被 @ 成员。没有可用对象时显示失败原因，不假装任务已经被接受。自然语言约束识别仍是保守短语匹配，尚非完整的语义约束解析。

协调仍沿用现有 RouteSchema（增加必需的 capability），服务端物化为 CatGroupDecision 的 Operations 和 Assignments。Operations 当前只生成 assign，后续补充、停止、状态查询等操作不能宣称已经支持。

### 11.2 持久化与去重

迁移 `0022_cat_group_requests.sql` 新增：

- `cat_group_requests`：请求 ID 复用 chainID，保存 clientMessageId、原始消息、接收背景、状态、决策和 first_reply_at。group/client 唯一；群删除级联清理。
- `cat_group_assignments`：稳定 ID 为 request/member/task 组合，保存不可变分工、capability、执行状态及 turnID。重复唤醒通过条件更新认领，不能重复启动同一派发。

用户消息与接收记录同事务保存。决策、全部派发（含 DAG 中尚未就绪节点）和初始工作流同事务提交。模型和进程执行期间不持有数据库事务；停止、派发和交付通过状态条件防止旧轮次恢复任务。

新前端发送失败后，在同一页面会话中重发相同内容和附件会复用原 clientMessageId；成功后再次发送相同内容会生成新 ID，允许用户有意重复提问。后端根据 ID 返回原接收结果。当前 ID 不跨页面刷新持久化，刷新后重发不具备相同的客户端去重保证。

### 11.3 固定执行输入与能力上限

接收时固定最近 20 条背景消息，完整保存本次正文和附件。协调器读取该快照；执行器使用同一原文、本次分工、仅供理解的背景与本任务依赖结果，不再从成员的未读游标拼接新任务。背景正文仍按预算截断，原始消息可追溯。

capability 为 chat / read_only / write。模型不能突破用户明确“只分析、不要修改”等限制；兜底任务固定 read_only。重试和改派保留原分工及能力，不因为切换成员而升级权限。适配器在选择传输方式、恢复会话之前处理限制，关闭 resume、live steer，改用临时受限会话。

| 适配器 | 当前受限模式与实际边界 |
| --- | --- |
| Claude | chat 禁用工具；read_only 使用 Read/Glob/Grep 白名单 |
| Codex CLI | 缺少经验证的无工具聊天模式，服务端将 chat 收紧为 read_only；使用全新只读沙箱，不能走 exec resume 继承可写会话 |
| Grok / CatBuild | 已验证开关为全部工具开/关；read_only 禁用全部工具，仅依据提供的上下文分析 |

这并未增加原生执行并发。受限模式和参数边界通过单元测试验证，尚未在真实提供方 CLI 上做端到端验证。

### 11.4 停止、重试和改派

群停止使旧生命周期失效；新消息建立新生命周期，旧队列的结束动作不能清理新队列。成员停止保留其他成员任务。普通请求与工作流任务改派只移除对应队列项，只取消对应 chain/turn，不取消原成员的无关请求。

改派时旧派发变为 superseded，新派发保存为 held；工作流负责人和预留节点与派发记录一起事务提交。旧进程退出后，held → pending 和节点释放也一起提交。等待移交期间拒绝再次改派或重试，以免绕过旧进程退出。交付需匹配 running 状态和当前 turnID，停止或改派后的迟到结果不能进群。

执行失败、空回复、超时沿用自动重试预算：最多 3 次，生产延迟 2/4/8 秒。显式停止不自动重启。重试耗尽后保留原因，可手动重试或改派。协调判断超时/结构无效采用有界判断和就绪成员降级；不是所有基础设施故障都会无限自动恢复。

### 11.5 重启恢复与回复监测

请求状态区分 received / routing / assigned / answered，以及 failed / stopped / interrupted。answered 表示已有成员有效答复，不表示整个协作图已经验收完成；协作完成仍以工作流状态为准。派发状态区分 pending / enqueued / running / retrying / held，以及 done / failed / stopped / interrupted / superseded。

启动恢复时：

- received 和中断在判断阶段的 routing 可重新判断；尚未执行的 enqueued 回到 pending，再按工作流依赖唤醒。
- 已执行的 running、等待重试的 retrying 和等待移交的 held 进入 interrupted，需要核查后明确重试，不盲目重复可能已发生的修改。
- 已有某位成员回复、但还剩待执行分工的请求，也能恢复剩余待办。

回复监测从接收开始覆盖分析、排队和执行，默认等待两分钟仍无首次有效答复时发出状态提示；不创建重复执行。接收回执、接单确认、自动重试提示与等待提示都不更新 first_reply_at。该提示为进程内一次性定时器，重启后根据请求记录重建，尚非持久化告警调度服务。

### 11.6 启用范围

有效新消息默认走新路径，没有新增 feature flag 或只对新群启用的灰度开关。旧请求历史保留兼容分支。新增数据库迁移会在应用正常启动迁移时应用；本次未提交 Git commit，也未替换用户正在运行的开发服务。
